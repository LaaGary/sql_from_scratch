Chapter 01 / Tour and skeleton

Start with a map: what is a database made of?

You probably use SELECT every day, but rarely stop to think about what happens behind those six letters. This tutorial starts from an empty folder and writes, in plain JavaScript, a SQL database that can persist, query, and run transactions. Chapter 1 draws the map first, then sets up the project skeleton.

Why write your own database?

Because a database is one of the few pieces of software you rely on every day but rarely take apart. Once you know how a row becomes a 4096-byte page, how a table is scanned, and how a transaction is recovered after a power loss, vague intuitions suddenly become concrete: why adding an index makes a query faster, why NULL can't be compared with =, and why even a small query can be slow.

And it's not as hard as it looks. An educational database engine has only three core jobs:

  • Read SQL: split text into tokens, then build a syntax tree (AST).
  • Compute results: scan, filter, group, sort, join.
  • Store results: page format, transaction journal, crash recovery.

This project builds those three parts in order. By the end you'll have a zero-dependency database you can open with node bin/sql.js, plus an engine you can play with in the browser.

Architecture: the journey of one SQL statement

Start with a picture. When you type this SQL:

SELECT title FROM books WHERE price > 100 ORDER BY title;

Inside our engine it passes through these stages:

StageModuleWhat it does
Tokenizingtokenizer.jsSplits the string into tokens such as word(SELECT), word(books)…, and records their positions.
Parsingparser.jsBuilds an AST from the tokens with recursive descent and reports syntax errors.
Evaluationengine/expr.jsTurns WHERE conditions and column expressions into values.
Query executionengine/query.jsScans, filters, groups, projects, sorts, and limits rows.
Storagetable.js, storage/*Rows live in memory or in pages; committed data is written to disk.
Interfacebin/sql.jsREPL: read a line, execute it, print the result as a table.

Each chapter covers one module (or a few). You'll find that the interfaces are small: the tokenizer returns only an array of tokens, the parser returns only plain objects, and the executor returns only a result object. Small interfaces are easier to test and easier to replace.

How to read this tutorial

Every chapter has a checkpoint: do the work, run the command, and if you see the same output, move on. Code blocks are the complete file at the end of the chapter (not fragments), so you can paste them straight into your project. Differences between chapters are marked with diff blocks.

Before you start: what you need

  • Node.js 18 or newer — the project has zero dependencies, so no npm install.
  • A terminal that can run commands (PowerShell on Windows and Terminal on macOS both work).
  • Basic JavaScript: objects, arrays, Map, class, async.

Build the skeleton: start with a REPL that only says hello

The first file is package.json. It's ordinary, but note "type": "module": everything uses ES modules, so the same code can later be bundled into the browser unchanged. 

{
  "name": "sql-from-scratch",
  "version": "1.0.0",
  "private": true,
  "type": "module",
  "scripts": {
    "repl": "node bin/sql.js",
    "test": "node --test"
  },
  "engines": { "node": ">=18" }
}

Next is bin/sql.js: a loop that reads input and answers built-in commands. It doesn't execute SQL yet — that's chapter 6 — but it wires up the path from user input to response.

bin/sql.jsJavaScript · 60 lines · step 1
#!/usr/bin/env node
/**
 * The sql-from-scratch command-line interface (CLI).
 *
 * Chapter 1: build a REPL skeleton that reads input and answers built-in commands.
 * Later chapters plug in the tokenizer, parser, and execution engine step by step.
 */
import { createInterface } from "node:readline/promises";
import process from "node:process";

const VERSION = "1.0.0";

const HELP = [
  "Built-in commands:",
  "  .help            show this help",
  "  .exit / .quit    quit",
  "",
  "This version has no SQL engine yet; entering SQL shows 'not implemented'."
].join("\n");

function printBanner() {
  console.log(`sql-from-scratch v${VERSION} — an SQL database built from scratch in JavaScript`);
  console.log("Type .help for commands, .exit to quit.");
}

async function main() {
  printBanner();
  const rl = createInterface({ input: process.stdin, output: process.stdout });
  rl.on("SIGINT", () => {
    console.log("");
    rl.close();
  });
  try {
    while (true) {
      let line;
      try {
        line = await rl.question("sql> ");
      } catch {
        break;
      }
      const input = line.trim();
      if (input === "") continue;
      if (input === ".exit" || input === ".quit") break;
      if (input === ".help") {
        console.log(HELP);
        continue;
      }
      if (input.startsWith(".")) {
        console.error(`Unknown command: ${input.split(/\s+/)[0]} (try .help)`);
        continue;
      }
      console.error("Not implemented yet: the SQL engine arrives in a later chapter.");
    }
  } finally {
    rl.close();
    console.log("Goodbye!");
  }
}

main();

Three things are worth noting:

  1. readline/promises: Node.js's built-in interactive input module. await rl.question("sql> ") waits until the user presses Enter before returning a line.
  2. try { ... } catch { } wraps rl.question: when the user presses Ctrl+D (or piped input ends), the promise is rejected; that's the normal way to exit.
  3. Dot commands (.help, .exit) are commands of the CLI itself, not SQL. Later chapters add .tables, .schema, and others.

Checkpoint — the REPL is alive

node bin/sql.js

sql-from-scratch v1.0.0 — a SQL database built from scratch in JavaScript Type .help for commands, .exit to quit. sql>

Type .help to see the available commands; type SELECT 1; and you'll see "not implemented". That's expected.

Build the right mental model: compiler + interpreter

Many tutorials make databases sound mysterious. Structurally, though, a database is a combination of two classic kinds of program:

  • The front half works like a compiler: string → tokens → syntax tree. This part runs once and is independent of the data.
  • The back half works like an interpreter: walk the syntax tree, scan data, compute results. This part runs once per row.

The split matters: the syntax tree for SELECT title FROM books is the same whether books has three rows or three million. So we can parse and validate the SQL first, then enter execution. Later, if you want more speed, you change the back half (add indexes, change the execution plan).

Chapter recap

  • A database engine consists of a tokenizer, parser, expression evaluator, query executor, storage layer, and CLI.
  • The project uses ES modules and has zero dependencies; steps/ keeps a complete snapshot of each chapter.

Exercises

  1. Add a .version command to the REPL that prints the VERSION constant.
  2. Make the REPL print nothing when it receives an empty line (the current code already skips empty lines — verify it).
  3. Think about it: if you replaced readline with a loop that reads a file, would the REPL still work?

Chapter glossary

REPL
Read-Eval-Print Loop: read a line, evaluate, print, repeat. Almost every database CLI works this way.
Token
The smallest unit of lexical analysis: keywords, identifiers, numbers, strings, operators.
AST
Abstract Syntax Tree: the structure of a statement represented as objects, ignoring parentheses and whitespace.
