Chapter 03 / Parsing

Make statements stand up: the parser and the syntax tree

Tokens have no structure of their own: SELECT name FROM books and FROM books SELECT name produce the same number of tokens. The parser's job is to decide whether these tokens, in this order, form a valid SQL statement, and to emit a syntax tree (AST) that the rest of the program can work with.

AST: describe the shape of a statement with objects

We want SELECT title FROM books WHERE price > 100 to become:

{
  type: "select",
  columns: [{ expr: { type: "column", name: "title" }, alias: null }],
  from: { name: "books", alias: null },
  joins: [],
  where: {
    type: "binary", op: ">",
    left:  { type: "column", name: "price" },
    right: { type: "literal", value: 100, valueType: "number" }
  },
  groupBy: [], having: null, orderBy: [],
  limit: null, offset: null, distinct: false
}

Why not execute while parsing? Because execution and syntax are two different concerns. With an AST, we can validate the whole statement before touching any data (no half-applied changes when a syntax error turns up late), optimize the AST (for example, remove WHERE 1 = 1), print it for debugging, or even store it for reuse.

AST nodes are plain objects

AST nodes are plain objects — no classes, no token references — so they can be passed straight to JSON.stringify. That's a big help for tests and debugging: the REPL's .ast command prints the AST as JSON.

Recursive descent: one grammar rule, one function

SQL's grammar is recursive: a SELECT contains expressions, and expressions contain parentheses and more expressions. The most direct implementation is one function per grammar rule, with the functions calling each other: 

parseStatement() -> look at the first keyword, dispatch to parseSelect / parseInsert / ...
parseSelect()    -> SELECT ... FROM ... WHERE ... GROUP BY ... ORDER BY ...
parseExpr()      -> expression (with precedence)
parsePrimary()   -> number, string, column, function call, parenthesized expression

Deciding "what comes next" only needs the current token, plus one or two tokens ahead when necessary (lookahead). Our parser has a single cursor, pos, along with a few small helpers: peek(), matchKeyword(), expectSymbol().

Expression precedence: 1 + 2 * 3 must not be 9

One function per binary operator would mean 5–6 nested levels, which is hard to read. Instead we use precedence climbing: each operator has a number, and parsing only consumes operators whose precedence is higher than the current threshold.

PrecedenceOperatorsAssociativity
1ORLeft-associative
2ANDLeft-associative
4= != < <= > >=, IS NULL, LIKE, IN, BETWEENLeft-associative
5|| (string concatenation)Left-associative
6+ -Left-associative
7* / %Left-associative
8Unary -, unary +Right-associative

NOT is special: its precedence is lower than the comparison operators. So NOT a = 1 is read as NOT (a = 1), not (NOT a) = 1. In code, NOT parses its operand with parseExpr(3), which picks up precedence-4 comparisons but not the precedence-2 AND.

Which statements are supported?

The grammar for the first version:

  • SELECT [DISTINCT] columns ... [FROM table [JOIN ...]] [WHERE ...] [GROUP BY ...] [HAVING ...] [ORDER BY ...] [LIMIT n [OFFSET m]]
  • INSERT INTO table [(columns...)] VALUES (...), (...)
  • UPDATE table SET column = value, ... [WHERE ...], DELETE FROM table [WHERE ...]
  • CREATE TABLE [IF NOT EXISTS] ..., DROP TABLE [IF EXISTS] ...
  • BEGIN / COMMIT / ROLLBACK

Deliberately out of scope: subqueries, UNION, ALTER TABLE, window functions. Keeping the scope small is how each piece gets done right. These topics make good extension exercises.

Syntax errors: point at the position, give a clue

Almost every parse function reports "expected X but found Y" and includes the current token's position. For example, SELECT * FROM; produces: 

SYNTAX_ERROR: expected a table name but found ';'
 1 | SELECT * FROM;
   |               ^

One more detail: expectIdentifier() rejects reserved words and suggests that "if the name is a reserved word, wrap it in double quotes". That's far more useful than a bare "syntax error".

Inspecting the AST with .ast

.ast SELECT id, COUNT(*) AS n FROM books GROUP BY id HAVING COUNT(*) > 1

Run that line and you'll get JSON: columns has two elements, groupBy has one column node, and having is a binary. Those nodes are the input for the executor in chapters 6–7.

Chapter recap

  • The parser turns tokens into an AST; the AST is plain objects, which makes testing, debugging, and later optimization easy.
  • Recursive descent maps one grammar rule to one function; precedence climbing handles binary operators.
  • Syntax errors always carry a position; when a reserved word is used as an identifier, suggest quoting it.

Exercises

  1. Support SELECT ... LIMIT ALL (the same as no limit). You'll need to change both the parser and the executor.
  2. Make the .ast command support .ast --raw to print unformatted JSON, easy to paste into another program.
  3. Add a CASE WHEN ... THEN ... ELSE ... END expression. Decide which layer it belongs to (primary?) before you start.

Chapter glossary

Recursive Descent
A parsing style where each grammar rule is written as a function, and the functions call each other.
Precedence Climbing
A parsing technique that handles binary operators with a "minimum acceptable precedence" parameter.
Lookahead
Looking ahead a few tokens to decide which grammar branch to take.
