Chapter 06 / SELECT pipeline

Your first real query: the SELECT execution pipeline

In the first five chapters we built tokens, a syntax tree, the value system, and tables — but we still can't query anything. This chapter connects the last pieces: the expression evaluator, the SELECT pipeline, write statements, and a CLI that can print tables. When you're done, you'll have a SQL database you can actually use.

The query pipeline: six stations of a SELECT

FROM     find the table, wrap each row as a "source list"
JOIN     attach rows from other tables (Chapter 9)
WHERE    keep only rows whose condition is TRUE
GROUP BY group rows (Chapter 7)
SELECT   compute the output columns
DISTINCT drop duplicate output rows
ORDER BY sort
LIMIT    take the first n rows

The executor doesn't do all of this at once; it transforms the data one stage at a time. This style (a simplified version of what database textbooks call the volcano model) lets you test each stage on its own, and makes optimizations easy to insert later: for example, adding a "look up a single row by primary key" shortcut right after FROM without touching any later stage.

What does a "row" look like at runtime?

A row during query execution isn't a single object; it's a source list: each source carries an alias, a table schema, and values. After a JOIN there are two or more sources, so we need to remember which table each value came from. 

[
  { alias: "b", table: booksSchema,   values: { id: 1, title: "JS" } },
  { alias: "a", table: authorsSchema, values: { id: 7, name: "Alice" } }
]

Why not merge the two tables into one object? Because after a JOIN there are often columns with the same name (both sides have id), and merging would clobber one of them. Only a source list can tell b.id from a.id, and can report "add an alias" when a column name is ambiguous.

Expression evaluation: turning an AST into a value

The evaluator is one big switch: a literal returns itself, a column looks itself up in the source list, a binary node dispatches on its operator, and a call invokes a function. A few implementation details are worth noting:

  • AND / OR must short-circuit: FALSE AND x doesn't need to evaluate x. But because SQL has three-valued logic, the short-circuit rule has to account for UNKNOWN: NULL AND FALSE is still FALSE.
  • NULL propagates through arithmetic: NULL + 1 is NULL; division by zero also returns NULL (rather than raising, which is SQLite's behavior).
  • Ambiguous column names must raise: if two sources have a same-named column and no alias disambiguates them, evaluateColumn throws AMBIGUOUS_COLUMN.

Implementing the SELECT pipeline

executeSelect builds the sources, scans the table, then pushes every row through WHERE, projection, DISTINCT, sorting, and LIMIT in that order. This version has no JOIN or grouping yet, so those statements produce an explicit "added in Chapter 7 / 9" error — a good error message tells you the next step, instead of just saying "not supported".

Projection and ORDER BY aliases

SELECT price * 2 AS double_price ... ORDER BY double_price is valid SQL. So when sorting, first check whether the ORDER BY expression is an alias of an output column; only if it isn't do we re-evaluate it against the source row. This small detail comes up again in Chapter 7 (sorting aggregates) and Chapter 9 (JOIN).

Write statements: CREATE / DROP / INSERT

Executing write statements is more direct: find the table, evaluate expressions into values, and call methods on Table. INSERT handles both the case with a column list and the case without one (schema order), and reports a clear error when the number of columns doesn't match.

Executor: dispatching the AST

This file is thin, but it's the single source of truth for which statements are supported. As each chapter adds statements, you only add one case here.

Public API: Database.exec()

We add exec() to Database: parse, execute statement by statement, and return an array of results. Each statement takes a snapshot first and restores it on failure — that's statement-level atomicity, and a preview of the transaction machinery in Chapter 10.

src/index.js is the entry point for external consumers. It deliberately exports only the core and never touches the file system, so the same code can be bundled for the browser as-is.

CLI: printing results as a table

The new bin/sql.js parses user input, executes it, and prints the results. A few details worth a look:

  • Multi-line input: if the statement isn't complete yet (say a CREATE TABLE is missing a closing paren), the REPL keeps waiting for the next line.
  • Full-width alignment: displayWidth() counts CJK characters as two cells so tables don't go crooked.
  • Error format: SqlError.format() prints a caret pointing at the error position.
  • Pipeline mode: node bin/sql.js < demo.sql executes line by line, which is handy for scripts.

Try it: your first complete database

Save the following as demo.sql:

CREATE TABLE books (
  id INTEGER PRIMARY KEY,
  title TEXT NOT NULL,
  author TEXT,
  price REAL DEFAULT 0
);

INSERT INTO books (id, title, author, price) VALUES
  (1, 'JavaScript: The Good Parts', 'Douglas Crockford', 320),
  (2, 'Designing Data-Intensive Applications', 'Martin Kleppmann', 680),
  (3, 'SQL Antipatterns', 'Bill Karwin', 450);

SELECT id, title, price FROM books
WHERE price > 300
ORDER BY price DESC LIMIT 5;

Then run:

node bin/sql.js < demo.sql

Passing this step means the core of the engine is done. The chapters that follow add features on top of it.

Chapter recap

  • A query is a pipeline: scan → filter → project → deduplicate → sort → limit.
  • A "row" at runtime is a source list, which is what lets us handle JOINs and ambiguous columns.
  • Expression evaluation has to handle three-valued logic, NULL propagation, and type conversion.
  • Database.exec() provides statement-level atomicity; the CLI makes results look good.

Chapter glossary

Query pipeline
Breaking a query into stages that run in order, where each stage passes a stream of data to the next.
Projection
Deciding which columns to output, i.e. the SELECT list.
Short-circuit evaluation
AND / OR stop evaluating the other side once the result is determined.
