Chapter 04 / Values and types

NULL is not 0: values, types, and comparison

If you've ever been burned by WHERE status <> 'done' dropping rows where status is NULL, this chapter explains why. A database's value system has a few more rules than JavaScript's, and those rules are the foundation of every query semantic that follows.

In our engine, TRUE / FALSE are just 1 / 0 (same as SQLite). That saves a type and lets boolean operations use numeric comparison directly.

NULL and three-valued logic

SQL comparisons aren't just true / false; they are true / false / UNKNOWN. Any comparison with NULL on either side yields UNKNOWN:

ExpressionResultWhy
NULL = 1UNKNOWNIs "unknown" equal to 1? No idea
NULL = NULLUNKNOWNTwo unknowns aren't necessarily the same unknown
NULL IS NULLTRUEIS NULL is a dedicated test, not a comparison
NULL AND FALSEFALSEWhatever the unknown is, AND FALSE is always false
NULL OR TRUETRUESame reasoning
NOT NULLUNKNOWNThe opposite of unknown is still unknown

WHERE keeps only rows whose result is TRUE. So WHERE price <> 100 does not select rows where price IS NULL. They are excluded not because they "aren't equal to 100", but because the comparison result is UNKNOWN. This is the most common NULL trap in practice.

Practical warning

If you mean "not 100, or unknown", you must say so explicitly: WHERE price <> 100 OR price IS NULL. The database won't guess for you.

Type affinity: '42' stored in an INTEGER column becomes 42

SQL is dynamically typed: a column's declared type isn't a hard restriction, it's a preference. Our applyAffinity() tries to convert values during INSERT:

Column typeInsert '42'Insert 42Insert 'abc'
INTEGER4242'abc' (stored as-is if it can't convert)
REAL4242'abc'
TEXT'42''42''abc'
BOOLEAN110 or 1 (based on truthiness)

This "lenient but predictable" conversion keeps beginners from getting stuck on type errors while preserving the behavior a database should have. If you want strict mode, change "can't convert" in applyAffinity to throw an error.

Comparison vs. ordering: two different things

SQL's = means "equal values", while ORDER BY needs a total order. The rules aren't quite the same. Our compareValues() defines the total order used for sorting: 

NULL  <  number (-∞ … +∞)  <  text (lexicographic)

So 3 < 'abc' is TRUE (numbers sort before text), but 3 = 'abc' is FALSE (different types are not equal). SQLite works the same way. This design gives us stable ordering even in mixed-type columns.

LIKE: SQL's wildcards

  • %: a string of any length (including zero).
  • _: exactly one character.
  • \%: escape; a literal %.

We implement it by translating the pattern into a regular expression. Note that SQLite's LIKE is case-insensitive for ASCII letters, so the regex gets the i flag. Before converting, escape the regex special characters, otherwise . becomes "any character".

Tests: pin down the semantics

Value-system tests don't need a database; calling the functions directly is enough. That also makes later debugging quick: is the comparison rule wrong, or the query pipeline?

Chapter recap

  • SQL has three-valued logic; comparing with NULL yields UNKNOWN, and WHERE keeps only TRUE.
  • Type affinity turns '42' into a number when it's stored in an INTEGER column.
  • Comparison (=) and ordering (ORDER BY) use different rules; numbers always sort before text.

Chapter glossary

Three-valued Logic
A logic system with true / false / UNKNOWN; SQL uses UNKNOWN for "don't know".
Type Affinity
A column's preference for a type; values are converted on write when possible, but it isn't a hard restriction.
Total Order
Any two values can be compared; sorting requires this relation.
