Chapter 08 / Updates and deletes

Making data move: UPDATE / DELETE and statement atomicity

So far we can only add data. This chapter adds modification and deletion, and handles a problem that's easy to overlook: if an UPDATE violates a constraint on the fifth row, should the changes to the first four rows stay? The answer is no.

How UPDATE works

  1. Find the target table, then check that every SET column exists (so a typo doesn't surface halfway through).
  2. Scan all rows and filter with the WHERE condition; with no WHERE, that's every row.
  3. Compute the new values for each row. Note: every assignment sees the old values.
  4. Hand the new values to Table.update(), which checks constraints and writes them back.

The third point matters. Consider this example: 

UPDATE books SET price = 1, stock = stock + 10 WHERE id = 2;

If we set price to 1 first and then compute stock + 10, the result doesn't change; but if the two assignments reference each other (SET a = b, b = a, a swap), the order affects the result. The SQL spec says: every value in one UPDATE is computed from the pre-change row. Our implementation computes the whole patch first and then hands it to Table in one go, so it gets this semantics for free.

How DELETE works

Filter the rows that match WHERE, then delete them one by one. Rows live in a Map keyed by rowid, so deletion is O(1). Deleted rowids are never reused, so "delete then insert" won't resurrect an old identifier.

Statement atomicity: roll the whole thing back on failure

Picture UPDATE books SET id = 1 WHERE id >= 2: changing the first row to 1 is fine, but the second hits the PRIMARY KEY. Without rollback, the database would be left in a half-updated state.

We already put the guard in Database.exec() in Chapter 6: take a snapshot before every statement, and call loadSnapshot() on error. This chapter just applies the same mechanism to the new statements and confirms with tests that it really works.

The cost of snapshots

Copying the whole database for every statement is fine at small data sizes, but it's wasteful. Chapter 10 uses "remember only the pages that changed" plus a transaction journal to do this efficiently — that's why real databases need a WAL / journal.

Chapter recap

  • UPDATE computes the new row in full before writing it back; every assignment uses the old values.
  • DELETE filters by WHERE and removes rows one by one; rowids are never reused.
  • A statement is an atomic unit: on failure the whole statement rolls back, leaving no partial changes.

Exercises

Chapter glossary

Atomicity
An operation either fully succeeds or doesn't happen at all.
Rollback
Restoring data to its state before the operation.
Old-value semantics
Every computation in one UPDATE uses the pre-change row.
