Chapter 07 / Aggregates and grouping

Turning many rows into one number: aggregates and GROUP BY

SELECT COUNT(*) FROM books returns a single row, and that row isn't any of the data rows — it's a summary of the whole table. That's aggregation: compressing a set of rows into one value. This chapter extends last chapter's query pipeline into two phases: group first, then compute per group.

Two cases: whole table and grouped

SyntaxSemanticsResult row count
SELECT COUNT(*) FROM booksthe whole table is one group1
SELECT author, COUNT(*) FROM books GROUP BY authorone group per authornumber of authors
SELECT COUNT(*) FROM books WHERE id > 99no rows match, but there's still one group1 (COUNT is 0)
SELECT author, COUNT(*) FROM books WHERE id > 99 GROUP BY authorno groups at all0

The last two rows are easy to get wrong. Without GROUP BY the whole table is always one group, even if it contains no rows; with GROUP BY, no rows means no groups, so the result has zero rows. That difference lives in buildGroups(): when groupBy.length === 0 it pushes a single group.

COUNT(DISTINCT author) is supported too: deduplicate, then count. Deduplication uses groupKey(), so the number 1 and the string '1' are not treated as the same value.

Aggregate state: evaluate each expression once

An aggregate expression can appear in SELECT, HAVING, and ORDER BY at the same time. For example: 

SELECT author, COUNT(*) AS n
FROM books
GROUP BY author
HAVING COUNT(*) > 1
ORDER BY n DESC;

COUNT(*) appears twice (SELECT and HAVING). Re-scanning the group on every evaluation would be much slower and would complicate the code. Our approach: collect all aggregate expressions in the query up front, build a cache for each group, and look the value up when evaluating. 

// a group object looks like this
{
  row: representativeRow,   // for non-aggregate columns (SQLite style: first row wins)
  rows: [ ... ],            // every row in this group
  state: {
    aggregate(expr) {       // look up the cache by the JSON-ified AST
      return cache.get(JSON.stringify(expr));
    }
  }
}

This also makes a query with aggregates but no GROUP BY work naturally: the whole table is one group, and the representative row is the first row.

Changes to the query pipeline

Introduce a unit concept for each row: with grouping, a unit is a group; without grouping, a unit is a single row plus an empty aggregate state. Projection, HAVING, and ORDER BY all evaluate against the unit.

SQLite's bare-column behavior

SELECT author, COUNT(*) FROM books is an error in standard SQL (author isn't in GROUP BY). SQLite allows it and picks an arbitrary row's value from the group. Our implementation matches SQLite: take the first row. Convenient, but it makes unexpected queries easy to write — in practice, put every non-aggregate column in GROUP BY.

Tests: aggregate edge cases

Aggregate tests need special attention to the empty set and NULL: over no non-NULL values, SUM is NULL, not 0, while COUNT(*) is 0. Those are the differences you actually run into in practice.

Chapter recap

  • An aggregate compresses a group of rows into one value; without GROUP BY the whole table is one group.
  • COUNT counts rows, the other aggregates ignore NULL, and the empty set behaves differently.
  • Aggregate results are cached so SELECT, HAVING, and ORDER BY share one computation.

Chapter glossary

Aggregate
A computation that compresses many rows into one value, such as COUNT or SUM.
Group
The set of rows that share a GROUP BY value.
HAVING
A condition that filters groups; WHERE filters rows, HAVING filters groups.
